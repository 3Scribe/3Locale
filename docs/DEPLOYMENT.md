# Deployment

3Locale Community supports Node/SQLite and Cloudflare Workers/D1. Both run the same application services, JSON/ZIP providers, UI and HTTP routes.

**This milestone has no authentication. Anyone who can reach an instance can read and modify its projects. Do not expose sensitive data or treat it as a shared production service.** Keep Node bound to loopback. For a hosted instance, restrict access at the deployment layer (for example Cloudflare Access) until application authentication is implemented. Access is optional external protection, not part of 3Locale's business logic.

## Node and SQLite

Use Node 24.15+ within Node 24 LTS:

```sh
npm ci
npm run dev
```

The default database is `data/three-locale.db`; server-only `THREELOCALE_DATABASE_PATH` selects another file. Production: `npm run build`, then `npm start`. Set `HOST=127.0.0.1` and `PORT=4321` for local-only access. SQLite migrations 1–3 remain unchanged and run automatically when the repository opens. Existing Milestone 3 files continue to work. Back up with a SQLite-aware tool, or stop the server before copying the database and WAL files.

## Local Cloudflare development

No Cloudflare account or credentials are needed:

```sh
npm ci
npm run cf:types
npm run db:migrate:local
npm run dev:cloudflare
```

Wrangler applies `migrations/d1` to the local D1 binding `THREELOCALE_DB`. Development uses workerd and persists D1 under `.wrangler/state`, independently of the Node SQLite file. Local migrations must be applied before first use and after schema updates.

```sh
npm run build:cloudflare
npm run preview:cloudflare
npm run test:d1
npm run test:cloudflare
```

The Cloudflare artifact is `dist-cloudflare`; the Node artifact is `dist`. The smoke test requires the Cloudflare build and installed Chromium (`npx playwright install chromium`). It creates a fresh, isolated local D1 database, applies Wrangler migrations, serves the built Worker and tests hydration, import/edit/export, stale requests, restoration and Arabic RTL. It does not deploy remotely.

`worker-configuration.d.ts` is generated by Wrangler; regenerate and commit it when bindings or compatibility settings change. Local `.wrangler`, `.astro-cloudflare`, generated builds and secret files are ignored.

## Manual deployment

Authenticate with the account that will own the Worker and D1 database:

```sh
npm ci
npx wrangler login
npx wrangler d1 create three-locale-community
```

Use the returned database ID for the `THREELOCALE_DB` binding in your local `wrangler.jsonc`. Keep account-specific IDs in your deployment configuration rather than contributing them to the Community repository. You can choose different Worker/database names; retain the binding name used by the runtime.

```sh
npm run db:migrate:remote
npm run build:cloudflare
npx wrangler deploy --config dist-cloudflare/server/wrangler.json
```

For subsequent deployments, `npm run deploy` performs the Cloudflare build, remote migrations, then deploys that artifact. A migration failure stops deployment. Always review pending forward migrations and arrange backups before updating a database containing valuable data. Worker code rollback does not undo D1 schema migrations.

## Deploy to Cloudflare

The official README button clones the repository into your account and uses the D1 resource described by `wrangler.jsonc`. Cloudflare supports provisioning D1 without a checked-in database ID. Review the unauthenticated-instance warning before proceeding.

Use Node 24 in Workers Builds. The `deploy` package script builds the Cloudflare artifact, applies remote migrations by binding name, and deploys the generated Worker configuration. Cloudflare can detect this script; ensure the deployment command is `npm run deploy`. The default `npm run build` builds Node only; the deployment script explicitly builds Cloudflare regardless. To avoid that extra Node build, set the build command to `npm run build:cloudflare` and the deploy command to `npm run db:migrate:remote && npx wrangler deploy --config dist-cloudflare/server/wrangler.json`.

For forks with a different Worker name, update `name` in Wrangler configuration to match the name selected in the deployment dashboard. Provisioning, account permissions and service quotas are controlled by Cloudflare. Repository CI validates everything locally without credentials; it does not create or test a live account deployment.

## Migrations, consistency and limits

SQLite retains its historical TypeScript migrations. D1 starts with `migrations/d1/0001_baseline.sql`, the current schema, using Wrangler's migration tracking. These are separate migration histories with the same logical application behaviour. After release, add a new migration; do not edit an existing migration. Physical SQLite-to-D1 file migration is out of scope; locale JSON import/export provides application-level portability.

D1 calculates changed rows using the previous and next project state. A manual translation edit writes only affected rows and its audit event, without creating a revision. Bulk writes bind JSON arrays, keeping parameter counts small. Full checkpoints use ordered text chunks below D1's per-row/string limit; chunks are reassembled only when reading a revision. Foreign keys and structural-path uniqueness preserve project and language ownership.

One D1 batch contains the version guard, state mutations, audit events, checkpoint chunks and retention. The first statement inserts a checked guard row only if the expected version matches (or the project is absent during creation). A mismatch fails the named constraint and rolls back the whole batch. The guard is removed before commit. No application-side read/check is used as the sole concurrency protection. Two writers with the same expected version cannot both commit. Retention keeps the newest 100 checkpoints independently per project; audit history is not pruned.

D1/Worker limits still apply: database capacity, per-invocation query counts, daily rows read/written, CPU, memory and query execution budgets vary by plan. Project state and checkpoints are currently materialised in memory; large accumulated projects and frequent full checkpoints can consume significant storage and CPU. Chunking solves the per-row snapshot limit, not unlimited project growth. Large imports/checkpoints can require a paid Worker plan to fit its higher query/CPU budget; a quota failure is returned as a safe error and does not partially commit. Imports retain existing limits (20 files, 10 MB total, 1 MB and 5,000 leaves per file). No R2, KV, queues or application Durable Objects are provisioned. Astro sessions are disabled and images use passthrough because neither service is required. No broad Node compatibility flag is enabled.

## Secrets and configuration

No current feature requires a secret. Do not create a placeholder credential to run 3Locale.

Future deployment credentials belong in Cloudflare Worker secrets (`npx wrangler secret put THREELOCALE_<NAME>`) and in an ignored `.dev.vars` file for local Worker development. Use the same `THREELOCALE_` convention with server-side environment configuration on Node. `.dev.vars*` and `.env*` are ignored; never put secrets in Wrangler `vars`, public Vite/Astro variables, React props, responses or logs. Runtime composition should read configuration and inject only the capabilities/settings application services need.

These are self-hoster deployment secrets. Future per-user or per-project credentials require separate application-managed secure storage, which is not implemented here. Cloudflare bindings are read only by `src/server/runtime.cloudflare.ts`; `process.env` stays at the Node composition boundary.
